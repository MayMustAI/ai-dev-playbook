# `/maymust:benchmark-checklist` — 성능 수치 검증

> 측정한 수치를 보고하거나 그 수치로 결정하기 전에 쓴다. PR의 전후 비교, 회귀 주장, 라이브러리·설정 선택이 대상이다. 각 질문에는 코드에 대한 추측이 아니라 실행에서 얻은 근거로 답한다.

사용자가 대략적인 수치만 원하면 1회 실행으로 충분하다. 그래도 질문 4와 7은 확인하고, 1회 실행임을 밝힌다. 그 실행이 이상해 보일 때만 나머지를 확인한다. 여러 선택지 중 하나를 고르는 비교는 대략적인 수치로 끝내지 않는다.

## 실행 전

- 내보낼 주장을 그대로 적는다. 예: "60k행 데이터셋에서 export p50이 30% 빨라졌다". 아래 질문은 이 문장을 검증한다
- 측정 스크립트를 읽고 무엇을 재고, 무엇을 세고, 무엇을 빼는지 적는다
- 머신 부하를 확인한다: `uptime`, 코어 수는 `nproc`(Linux) 또는 `sysctl -n hw.ncpu`(macOS). 부하가 높으면 원인을 찾고, 멈출 수 없으면 양쪽을 번갈아 실행해 같은 잡음을 받게 하고 보고에 적는다

## 7개 질문

1. **왜 두 배가 아닌가?** 한계 요인을 이름으로 댄다: 코어, 락, 디스크, 네트워크, 부하 생성기 자체. 보고하지 않는 별도 실행에서 프로파일링한다(프로파일러는 작업을 느리게 한다). 프로세스별 CPU(`top`, `pidstat`), 런타임 프로파일러(`node --cpu-prof`, `py-spy`, `perf`), I/O 대기, 시스템 콜 수(Linux `strace -c`)를 보고 병목을 소스에 대응시킨다. 부하 생성기가 먼저 포화되면 부하 생성기를 잰 것이다. 변경이 수치를 움직이지 못했다면 한계 요인이 그 이유를 설명하므로, 변경을 쓸모없다고 판단하기 전에 한계 요인부터 찾는다.
2. **튜닝했나?** 모든 쪽을 운영 환경과 같은 방식으로 실행한다: 릴리스 빌드, 운영 플래그와 환경 변수, 배치·트랜잭션 설정, 커넥션 풀, 운영과 같은 캐시 상태, 같은 버전과 데이터. 한쪽만 기본값이면 구현이 아니라 설정을 비교한 것이다. 한계 요인이 설정(행마다 커밋, 디버그 빌드, 인덱스 누락)이면 그쪽은 튜닝되지 않은 것이다. 튜닝하고 다시 잰 뒤에 승자를 고른다. 튜닝할 수 없으면 그 실행으로 승자를 고르지 않는다.
3. **물리적 한계를 넘었나?** 계산해 본다. 초당 바이트를 디스크·네트워크 대역폭과, 초당 연산 수와 연산당 비용의 곱을 코어 수와, 줄어든 시간을 바뀐 부분이 원래 차지하던 시간과 비교한다. 전체의 10%를 차지하던 부분을 없애도 전체는 최대 약 11%만 빨라진다. 한계를 넘는 결과는 캐시, 아무 일도 하지 않은 실행, 버그처럼 작업이 아닌 다른 것을 잰 것이다.
4. **오류가 났나?** 실패와 비정상 응답 수를 센다. 출력이 존재하는지가 아니라 올바른지 확인한다. 거절은 빠르고 타임아웃과 재시도는 느리다. 스크립트가 오류를 세지 않으면 세도록 고친다.
5. **재현되나?** 양쪽을 최소 5회씩 번갈아(A, B, A, B, …) 실행해 워밍업, 지연 초기화, 캐시, 드리프트가 한쪽에 유리하지 않게 한다. 중앙값과 범위를 보고한다. 차이가 실행 간 편차보다 작으면 측정 가능한 차이가 없는 것이다. 판정이 아슬아슬하면 순위합 검정이나 측정 도구의 통계를 쓴다.
6. **중요한가?** 마이크로 결과 옆에 사용자가 실제로 기다리는 전체 경로를 현실적인 데이터 크기와 동시성으로 재고, 마이크로 결과를 전체 대비 비중으로 보고한다. 요청 시간의 1%를 차지하는 헬퍼는 아무리 빨라져도 요청을 최대 1%만 빠르게 한다.
7. **작업이 실제로 일어났나?** 측정 구간 안에서 작업이 실행됐는지 확인한다: 요청이 서버에 도달했는지, 행이 쓰였는지, 바이트를 읽었는지, 코드가 결과를 사용했는지. 아무도 순회하지 않는 제너레이터, 아무도 await하지 않는 promise, JIT가 버릴 수 있는 결과, 타임아웃은 일어나지 않은 작업의 수치를 만든다.

## 수치를 설명할 수 있어야 한다

- "왜 두 배가 아닌가"에 답하지 못하면 무엇을 쟀는지 모르는 것이다. 코드를 읽고 한 추측은 한계 요인이 아니다
- 수치가 다른 것을 쟀을 가능성(오류, 건너뛰거나 캐시된 작업, 실행되지 않은 코드, 튜닝되지 않은 한쪽, 잡음, 전체에서 너무 작은 부분)을 나열하고 근거로 하나씩 배제한다
- 평가(eval) 결과에도 같은 질문을 적용한다: 모든 시행이 과제를 수행했는지, 차이가 시행과 모델에 걸쳐 유지되는지, 시나리오가 중요한지

## 보고

- 판정을 먼저 쓴다: 빨라짐, 느려짐, 측정 가능한 차이 없음, 판단 불가
- 수치는 단위, 실행 횟수, 범위, 한계 요인과 함께 쓴다. 예: "p50 41 ms → 33 ms, 쪽당 7회 중앙값, 변경 후 범위 32~35 ms, 단일 코어의 JSON 파싱이 한계"
- 차이를 주장하면서 한계 요인을 대지 못하거나, 한쪽이 튜닝되지 않았거나, 질문 4와 7을 확인하지 못했으면 판정을 "판단 불가"로 하고 빠진 부분을 적는다
- PR 본문에는 대표 수치 하나(단위, 전후, 실행 횟수)를 쓰고, 나머지 실행 기록·범위·한계 요인 근거는 worklog나 별도 파일에 두고 링크한다

## 금지 사항

- ❌ 1회 실행으로 선택지 비교의 결론 내기
- ❌ 실행 횟수·범위·한계 요인 없이 수치만 보고하기
- ❌ 바뀐 부분이 원래 차지하던 시간보다 큰 개선을 그대로 보고하기 — 다른 것을 잰 것이다
- ❌ 프로파일러를 켠 실행의 수치를 보고하기
