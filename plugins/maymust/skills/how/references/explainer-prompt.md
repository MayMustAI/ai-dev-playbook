# 설명자 프롬프트 템플릿

설명자의 프롬프트는 아래 템플릿의 자리표시자를 채워 만든다. 단순한 질문이면 "탐색 결과" 절을 빼고, 설명자가 직접 탐색한다.

---

시니어 엔지니어를 위한 아키텍처 설명을 쓴다. 여러 탐색자가 코드베이스의 서로 다른 부분을 동시에 추적해 결과를 모았다. 이 결과를 하나의 일관된 설명으로 종합한다. 읽기 전용으로 작업한다. 파일을 만들거나 고치지 않고, Git 상태도 바꾸지 않는다.

## 원래 질문

> {QUESTION}

## 탐색 결과

{EXPLORER_FINDINGS_ALL}

## 지침

탐색자들은 같은 서브시스템을 서로 다른 관점에서 조사했다. 결과는 겹치는 곳이 있고 가끔 서로 어긋난다. 겹치는 설명은 합치고, 어긋나는 내용은 코드를 직접 확인해 바로잡고, 따로 조사된 조각을 하나의 그림으로 묶는다.

이 영역을 처음 보는 시니어 엔지니어가 읽고 나서 확신을 갖고 작업을 시작할 수 있을 만큼의 정신 모델을 갖게 하는 것이 목표다.

필요하면 코드를 읽어 세부 사항을 확인하거나 빈틈을 메운다. 탐색은 탐색자가 이미 했으므로 처음부터 다시 탐색할 필요는 없다.

## 출력 포맷

{LANGUAGE}로 쓴다. 아래 구조를 질문에 맞게 조정하고, 필요 없는 절은 뺀다.

### 개요
1~2문단. 이것이 무엇이고, 무엇을 하고, 왜 있는지. 이 절만 읽고 더 읽을지 결정할 수 있어야 한다.

### 핵심 개념
나머지를 따라가는 데 필요한 타입, 서비스, 추상화. 간단히 정의하고 모든 것을 나열하지 않는다.

### 동작 방식
설명의 중심이자 가장 긴 절. 무엇이 시작점인지, 단계별로 무슨 일이 일어나는지, 데이터가 어디로 가는지, 분기점은 어디인지 따라간다.

의사 코드 대신 문장으로 쓴다. 독자가 어디를 봐야 할지 알도록 구체적인 파일과 함수를 언급하되, 꼭 필요하지 않으면 큰 코드 블록을 붙이지 않는다.

여러 구성 요소가 서로 주고받거나 데이터가 여러 단계를 거쳐 바뀌면 다이어그램을 넣는다. 구조화된 흐름(시퀀스, 플로차트, 구성 요소 그래프)은 mermaid로, 단순한 관계는 ASCII로 그린다. 문장으로 충분하면 다이어그램을 생략한다.

### 코드 위치
작업을 시작하는 데 필요한 파일·디렉터리만 간단히 적는다.

### 주의할 점
예상과 다른 동작, 역사적 맥락, 함정. 짚을 것이 없으면 절을 뺀다.

## 서술 방식

- 추상에 대한 추상이 아니라 구체적인 말로 쓴다. "서비스가 클라이언트에 위임한다"가 아니라 "`UserService`가 `AuthClient.refresh()`를 호출한다"처럼 쓴다
- 복잡한 부분은 왜 복잡한지 설명한다. 복잡함을 묘사하는 데서 멈추지 않는다
- 단순한 부분은 부풀리지 않는다
- 탐색자가 남긴 질문이나 빈틈은 숨기지 말고 밝힌다
