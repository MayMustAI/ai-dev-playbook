# 장문 문서 (Notion 기준, Confluence·Google Docs에도 적용)

## 이 출처에 있는 것

- PRD(제품 요구 문서)
- 기술 스펙과 RFC
- ADR(아키텍처 결정 기록)
- 설계 리뷰 회의록
- 도메인 맥락을 담은 팀 페이지
- 장애 회고(포스트모템)
- 방어 코드를 설명할 수 있는 런북
- 우선순위를 정한 전략 문서

"왜"는 코드가 되기 전에 긴 문서로 먼저 쓰이는 경우가 많다. 중요한 기능에는 보통 문서가 있다.

## 찾는 방법

Notion MCP를 쓴다(예: `notion-search`, `notion-fetch`). 도구 이름은 MCP마다 다를 수 있으므로 스키마를 먼저 확인하고, 검색·조회 도구만 쓴다. 페이지·댓글을 만들거나 고치는 도구는 쓰지 않는다.

1. **키워드 검색.** 다음을 시도한다.
   - 기능 이름
   - 대상 코드의 핵심 심볼·클래스 이름
   - 작성자 이름(설계 문서는 코드보다 먼저 쓰이는 경우가 많다)
   - 오류 문자열이나 사용자에게 보이는 용어
   - 코드가 배포된 시점을 안다면 기간을 좁힌 검색
2. **후보 페이지 전체 읽기.** 미리보기가 아니라 전체를 가져와 읽는다. 이유는 문서 중간에 묻혀 있는 경우가 많다.
3. **백링크와 하위 페이지 따라가기.** 설계 문서에는 검토한 대안, 부록, 구현 메모가 하위 페이지로 있는 경우가 많다.
4. **관련 데이터베이스 확인.** 데이터 소스 조회나 회의록 조회 도구로 그 결정을 논의한 회의록을 찾는다.
5. **작성자의 개인 공간 확인.** PR 작성자의 개인 노트에 코드에 앞선 탐색 기록이 있을 수 있다.

## 좋은 근거의 모습

- 대상 코드의 목적과 맞는 "문제 정의"나 "동기" 절이 있는 PRD
- "검토한 대안"이나 "기각한 방법" 절
- 대상 코드를 특정 장애의 수정으로 지목한 포스트모템
- PR과 같은 작성자·기간에 "Y 때문에 X로 결정"을 기록한 회의록
- 상태·맥락·결정·결과가 실제로 채워진 ADR

## 흔한 함정

- **오래된 문서.** 스펙은 구현 전에 쓰이고 갱신되지 않는 경우가 많다. 실제 PR과 대조한다.
- **문서와 현실의 차이.** 스펙은 "X를 한다"인데 코드는 Y를 한다면 그 차이를 표시한다. 종합자가 어긋남으로 드러낸다.
- **형식적인 템플릿.** 상투적인 "Why" 절보다 구체적인 내용을 찾는다.
- **연결되지 않은 문서.** 가장 관련 있는 문서가 어디에도 링크되어 있지 않을 수 있다. 넓은 키워드 검색이 도움이 된다.
- **여러 초안.** 같은 주제의 문서가 여럿이면 확정되었거나 가장 최근에 갱신된 것을 찾는다. 날짜를 확인한다.
- **접근 제한.** 볼 수 없는 페이지는 빈틈으로 기록한다.

## 돌려줄 것

관련 문서마다:
- 제목과 URL
- 작성자와 마지막 수정일
- 동기에 해당하는 원문 인용과 페이지·절 위치
- 관련 링크 페이지(종합자가 인용할 수 있게)
- 확정본인지 초안인지
