# 이슈 트래커 (Linear 기준, Jira·GitHub Issues에도 적용)

## 이 출처에 있는 것

- 기능·버그와 그 동기를 설명하는 이슈
- 이슈에 붙은 프로젝트 문서(PRD, 스펙)
- 상위·하위 이슈 관계(큰 이니셔티브에서 구체적 티켓으로)
- 이슈 댓글(범위 변경, "왜 하는지"에 대한 설명)
- 동기의 종류를 알려 주는 라벨(`compliance`, `customer-request`, `perf` 등)
- 범위 변경을 설명하는 상태 업데이트
- 첨부 파일과 연결된 GitHub PR

"고객 X가 요청해서", "3분기 컴플라이언스 이니셔티브 때문에" 같은 제품·비즈니스 맥락이 주로 여기에 있다.

## 찾는 방법

Linear MCP를 쓴다. 도구 이름은 MCP 버전마다 다를 수 있으므로 스키마를 먼저 확인하고, 조회·검색 도구만 쓴다.

1. **연결된 티켓부터.** 시작 커밋이나 PR에 티켓 ID(`ENG-1234`, `[BUG-567]` 등)가 있으면 그 이슈를 먼저 가져와 댓글까지 전부 읽는다.
2. **키워드로 관련 이슈 찾기.** 기능 이름, 핵심 심볼, 비즈니스 용어로 여러 표현을 시도한다.
3. **이슈 트리 따라가기.** 하위 이슈에 도착했다면 상위 이슈를 가져온다. 하위 이슈는 실행 단위이고, 상위 이슈에 "왜"가 있는 경우가 많다.
4. **프로젝트 문서 읽기.** 이슈가 프로젝트에 속하면 프로젝트와 첨부 문서를 확인한다. 스펙과 이유가 가장 자주 기록되는 곳이다.
5. **라벨과 마일스톤 확인.** 라벨은 동기의 종류를, 마일스톤은 마감과 연결된 동기를 드러낸다.

## 좋은 근거의 모습

- 비즈니스 문제를 말하는 이슈 본문: "고객 A의 SOC2 감사 때문에 X가 필요하다"
- 결정을 기록한 댓글: "A안은 결제 서비스를 건드려야 해서 B안으로 간다"
- 이니셔티브 이름을 가진 상위 이슈: "3분기 엔터프라이즈 준비", "결제 실패 줄이기"
- 첨부된 PRD나 스펙
- `customer:acme`, `incident-followup`, `compliance`, `perf-regression` 같은 라벨

## 흔한 함정

- **범위 변화.** PR이 참조한 티켓이 닫혔다가 다른 범위로 다시 열렸을 수 있다. 전체 이력을 읽는다.
- **형식적인 템플릿.** "Why" 절을 상투적인 문장("사용자 경험 개선")으로 채운 경우는 실제 답이 아닐 가능성이 높다.
- **오래된 티켓.** 계획이 바뀌기 전의 내용일 수 있다. 날짜를 확인하고 코드가 배포된 시점과 맞춰 본다.
- **중복 처리 사슬.** "중복으로 닫힘" 관계를 따라 원래 티켓까지 간다.
- **접근 권한.** 볼 수 없는 이슈는 추측하지 말고 빈틈으로 기록한다.

## 돌려줄 것

관련 티켓마다:
- 티켓 ID와 제목
- 본문이나 댓글에 있는 문제·동기의 원문 인용(요약하지 않는다. 종합자가 정확한 문장을 인용해야 한다)
- 라벨, 상위 이슈, 프로젝트
- 작성자, 생성일, 종료일
- 링크(있으면)
