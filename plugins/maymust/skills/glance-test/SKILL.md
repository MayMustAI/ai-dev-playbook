# `/maymust:glance-test` — 슬라이드 3초 점검

> 청중은 글을 읽으면서 동시에 말을 듣기 어렵다. 슬라이드는 광고판처럼 3초 안에 메시지 하나를 전해야 한다.

## 호출 예

```
/maymust:glance-test talk/deck.html
/maymust:glance-test slides.pdf 1920x1080
/maymust:glance-test deck.pptx 3장은 "설치는 main 채널에서"를 전해야 함
```

## 실행 방식

- 점검 단계에서는 덱을 고치지 않는다. 이미지와 측정 결과는 저장소 밖 임시 디렉터리에 둔다
- 서브에이전트를 쓸 수 있으면 판독을 별도 검토자에게 맡긴다. 검토자는 이 대화를 물려받지 않고 프롬프트만 받는 새 서브에이전트여야 한다. Claude Code에서는 대화를 포크하지 않는 일반 서브에이전트(예: `general-purpose`)를 쓰고, Codex의 `spawn_agent`처럼 대화를 물려줄지 고르는 도구는 물려주지 않게(예: `fork_turns: "none"`) 띄운다
- 서브에이전트를 쓸 수 없거나 대화 상속을 끌 수 없으면 같은 세션에서 판독하고, 의도를 아는 상태라 앵커링 편향이 있을 수 있다는 점을 보고서에 밝힌다. 같은 세션에서 판독할 때는 발표자 노트와 의도를 다시 읽기 전에 판독 결과를 먼저 적어 둔다
- 검토자에게는 이미지 경로와 화면 크기만 준다. 덱 파일, 덱 제목, 발표자 노트, 의도한 메시지는 주지 않는다. 이미지 이름은 `slide-01.png`처럼 내용이 드러나지 않게 둔다
- 장이 20장을 넘으면 20장 안팎으로 나눠 검토자 여러 명에게 맡긴다. "반복 템플릿"처럼 여러 장에 걸쳐 드러나는 원인은 나눈 경계에서 놓칠 수 있으므로 직접 이미지를 훑어 확인한다

## 판정 기준

| 판정 | 기준 |
| --- | --- |
| PASS | 3초 안에 메시지 하나가 잡힌다 |
| BORDERLINE | 메시지는 잡히지만 경쟁 요소 때문에 읽어야 한다 |
| FAIL | 3초를 훨씬 넘게 읽어야 하거나 메시지가 하나로 모이지 않는다 |

## 워크플로우

1. **대상 확인** — 덱 파일(HTML, PDF, PPTX, 이미지 묶음)과 발표 화면 크기를 확인한다. 크기를 모르면 1600×900을 쓴다. 발표자 노트나 작성자가 밝힌 의도가 있으면 함께 받는다. 고칠 때 지켜야 할 것(사용자가 정한 문구, 그대로 인용해야 하는 원문, 사용자가 직접 요청한 요소)이 대화에 있으면 적어 둔다
2. **렌더링** — 장마다 발표 크기의 이미지를 만든다. 애니메이션이 있으면 최종 상태를 찍는다. 아래에서 쓸 수 있는 방법을 고르고, 방법이 없으면 사용자에게 장별 스크린샷을 요청한다
   - HTML: [render_html.py](scripts/render_html.py)를 쓴다(Python 3, Chrome 필요). 장별 이미지와 객관 지표를 JSON으로 함께 낸다. 덱 코드에서 장을 넘기는 방식을 확인하고 그에 맞춰 호출한다

     ```bash
     # 장이 한 페이지에 세로로 이어진 덱
     python3 <skill-dir>/scripts/render_html.py --out <tmp> --size 1600x900 --selector "section.slide" deck.html > <tmp>/slides.json
     # 한 번에 한 장만 보이는 덱: 장을 바꾸는 코드를 --show에 넣는다(i는 0부터 세는 장 번호, el은 그 장의 요소)
     python3 <skill-dir>/scripts/render_html.py --out <tmp> --selector ".slide" --show "Reveal.slide(i);" deck.html > <tmp>/slides.json
     # 장마다 파일이나 URL이 따로 있는 덱: 순서대로 나열한다
     python3 <skill-dir>/scripts/render_html.py --out <tmp> deck.html#1 deck.html#2 deck.html#3 > <tmp>/slides.json
     ```

     CSS 애니메이션과 전환은 스크립트가 끝 상태로 보낸다. 클릭할 때마다 하나씩 나타나는 요소처럼 덱 코드가 보여 주는 요소는 `--show`에서 모두 보이게 만든다
   - PDF: `pdfinfo deck.pdf`의 Page size로 페이지 비율을 확인하고, 장 전체가 발표 화면(W×H) 안에 들어가도록 한 변을 맞춘다. 페이지가 화면보다 가로로 길거나 비율이 같으면 `pdftoppm -png -scale-to-x W -scale-to-y -1 deck.pdf <tmp>/slide`, 세로로 길면 `-scale-to-x -1 -scale-to-y H`를 쓴다. 결과 이미지가 W×H 안에 드는지 확인하고, 비율이 달라 실제 화면에서 여백이 생기면 보고서에 밝힌다
   - PPTX: LibreOffice로 PDF를 만든 뒤(`soffice --headless --convert-to pdf --outdir <tmp> deck.pptx`) PDF처럼 처리한다
   - 이미지 묶음: 그대로 쓰고, 비율이 발표 화면과 다르면 보고서에 밝힌다
3. **맥락 없는 판독** — [reader-prompt.md](references/reader-prompt.md)를 채워 검토자에게 맡긴다. 검토자는 장마다 판정, 처음 눈이 가는 곳, 3초 뒤 남는 메시지 한 문장(없으면 "불분명")을 내고, BORDERLINE과 FAIL에는 주된 원인과 구체적인 수정안 하나를 붙인다
4. **객관 지표** — 원본에 접근할 수 있으면 장별로 보이는 글자 수, 시각 단위(카드·행·항목) 수, 실제로 렌더링된 가장 작은 글자 크기를 잰다
   - HTML: 렌더링 결과의 `chars`, `units`(`boxes`는 카드·상자, `items`는 목록 항목과 표의 행), `min_font_px`를 쓴다. `max_font_px`와 `max_font_text`로는 가장 크게 보이는 글자가 메시지인지 주제어인지 확인한다. 다른 브라우저 도구로 렌더링했다면 [measure_slide.js](scripts/measure_slide.js)를 장마다 페이지에서 실행해 같은 정의로 잰다
   - PDF·PPTX: `pdftotext -f <N> -l <N> deck.pdf -`로 장별 글자 수를 센다. 시각 단위 수와 글자 크기는 이미지에서 어림잡고 "추정"으로 표시한다
   - 숫자는 판정의 근거로만 쓴다. 기준값을 정해 놓고 기계적으로 판정하지 않는다
5. **대조와 확인**
   - 3초 뒤 남는 메시지를 의도한 메시지와 비교한다. 의도는 사용자가 밝힌 것, 발표자 노트, 덱 내용 순으로 찾고, 덱 내용에서 추론한 의도는 "추론"으로 표시한다
   - 깔끔해 보여도 남는 메시지가 의도와 다르면 PASS가 아니다. 의도의 일부만 남으면 BORDERLINE, 다른 메시지가 남으면 FAIL로 바꾸고 이유를 적는다
   - 검토자가 FAIL로 판정한 장 가운데 2~3장(적으면 전부)은 직접 이미지를 보고 확인한다. 검토자의 보고는 단서이지 증거가 아니다. 판정을 바꾸면 이유를 적는다
6. **보고** — 아래 [보고 형식](#보고-형식)에 맞춰 한국어로 보고한다
7. **수정 범위 확인** — 점검 단계에서는 고치지 않는다. 보고서 끝에서 고칠 범위를 묻는다: 전부 / 제목과 군더더기만 / 실패 장만. 고친 뒤에는 바뀐 장만 다시 렌더링하고, 새 검토자에게 같은 방식으로 판독을 맡겨 수정 전후 판정을 보여 준다

## 점검 패턴

실제 덱에서 자주 나온 원인이다. 원인을 적을 때 이 이름을 먼저 쓰고, 맞는 것이 없으면 새 이름을 붙인다.

| 패턴 | 증상 | 고칠 방향 |
| --- | --- | --- |
| 주제어 제목 | 가장 큰 글자가 주제어("설치", "PR")이고, 메시지는 그 아래 작은 부제에 있음 | 메시지를 제목으로 올리고 주제는 작은 태그로 내린다 |
| 각주에 숨은 규칙 | 가장 중요한 규칙이 맨 아래 각주에 있음 | 규칙을 제목이나 본문 첫 줄로 올린다 |
| 같은 무게의 나열 | 같은 무게의 카드가 나란히 있어 시선이 들어갈 곳이 없음 | 핵심 하나를 키우거나 강조하고, 나머지는 줄이거나 다른 장으로 나눈다 |
| 반복 템플릿 | 같은 템플릿이 이어져서 장이 바뀐 줄 모름 | 장마다 달라지는 핵심 요소를 가장 크게 둔다 |
| 세부 자료 상자 | 어두운 코드·표 상자가 시선을 가장 먼저 끌지만, 그 안에 든 것은 세부 자료임 | 상자를 줄이거나 톤을 낮추고, 전체 내용은 노트나 부록으로 옮긴다 |
| 엉뚱한 강조색 | 강조색이 아직 도입 전이거나 덜 중요한 항목에 가 있음 | 강조색은 이 장의 메시지에만 쓴다 |
| 발표 화면에서 안 되는 요소 | 마우스를 올려야 보이는 안내처럼, 발표 화면에서는 작동하지 않는 요소가 있음 | 화면에 바로 보이게 하거나 말로 전하고, 세부는 노트로 옮긴다 |
| 읽기용 글자 | 뒤쪽 좌석에서 읽기 어려운 작은 글자가 있음 | 분량을 줄여 글자를 키우고, 세부는 배포 자료로 옮긴다 |

## 보고 형식

```markdown
## 글랜스 테스트: <덱 이름> (<N>장, <W>×<H>)

판독: <별도 검토자 | 같은 세션(의도를 아는 상태라 앵커링 편향 가능)>

- PASS <a>장 · BORDERLINE <b>장 · FAIL <c>장
- 통과한 장의 공통점: <다른 장을 고칠 때 따를 특징>. 본보기: <장 번호>

### 실패 장

| 장 | 3초 뒤 남는 것 | 원인 | 고칠 방향 |
| --- | --- | --- | --- |
| <번호> | <한 문장 또는 "불분명"> | <패턴 이름과 근거 지표> | <구체적인 수정 하나> |

### 경계 장

- **<패턴 이름>** (<장 번호>): <공통 원인과 고칠 방향>

### 고칠 때 지킬 것

- 사용자가 정한 문구: <없으면 "확인 필요">
- 그대로 인용해야 하는 원문: <…>
- 사용자가 직접 요청한 요소: <…>

### 화면에서 빠질 세부 자료를 옮길 곳

- <장 번호> <자료>: 발표자 노트 / 부록 / 배포 자료

어디까지 고칠까요? 전부 / 제목과 군더더기만 / 실패 장만
```

- 원인 칸에는 판정의 근거가 된 지표를 함께 적는다. 예: "주제어 제목: 가장 큰 글자는 '설치'(96px), 메시지는 18px 부제"
- 의도와 대조하거나 직접 이미지를 보고 판정을 바꾼 장은 표시하고 이유를 적는다
- 고친 뒤의 재판독은 `| 장 | 수정 전 | 수정 후 | 3초 뒤 남는 것 |` 표로 보여 준다
